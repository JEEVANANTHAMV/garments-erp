1. Objective
The ERP shall maintain a complete, version-controlled BOM for every garment Style and calculate material requirements based on Buyer PO, Style, Colour, Size and order quantity. The same BOM engine shall support Yarn, Fabric, Trims, Accessories, Packing and General Materials without duplicating core logic.
Support style-level, colour-level, size-level and colour-size-level material definitions.
Support different consumption bases such as per piece, per dozen, per carton, per set and fixed quantity.
Calculate base requirement, additional quantity, wastage and final requirement automatically.
Separate BOM requirement from purchase requirement, stock, issue, actual consumption, return and wastage.
Maintain BOM revisions so historical transactions are never changed by later master edits.
Provide full traceability from Buyer PO → Style → BOM → Material Requirement → Purchase → GRN → Stock → Issue → Actual Consumption.

3. Overall BOM Hierarchy
Recommended logical hierarchy:
Garment Style → Garment BOM → Yarn / Fabric / Trims / Accessories / Packing / General Materials
For material transformation, a multi-level relationship may be used:
Yarn → Knitting → Grey Fabric → Dyeing/Printing/Washing/Compacting → Finished Fabric → Cutting/Sewing → Finished Garment
4. BOM Design Principle
Use one common BOM header/detail engine with bom_type rather than creating six unrelated BOM modules.
Use process-specific fields only where required (e.g., Fabric GSM/Width, Yarn Count, Packing Ratio).
Do not overwrite approved BOMs. Create a new revision.
Freeze the BOM revision, consumption and conversion values used when a requirement or transaction is posted.
Master changes must not change historical purchase, issue or consumption transactions.

11. Requirement Calculation
Core calculation:
Base Qty = Applicable Order Qty × Consumption
Wastage Qty = Base Qty × Wastage %
Final Requirement = Base Qty + Additional Qty + Wastage Qty
Example: Order Qty 1,000 PCS × Fabric consumption 0.82 KG = 820 KG. At 5% wastage, wastage = 41 KG. Final requirement = 861 KG.

20. Material Requirement Flow
Select Buyer PO.
Load Style and colour-size order matrix.
Load Active/Approved BOM revision.
Calculate material requirement.
Display colour-wise and size-wise requirement.
Check available stock and reserved stock.
Check open purchase orders.
Calculate net purchase requirement.
Create Material Request / Purchase Requirement.
Link purchase and GRN transactions back to requirement.
21. Net Purchase Requirement
Net Purchase Requirement = Gross Requirement − Available Stock − Reserved Stock − Open PO Quantity.
Example: Requirement 861 KG; Available stock 300 KG; Open PO 200 KG; Net purchase requirement = 361 KG.

27. Validation Rules
Buyer, Style and BOM Type are mandatory.
Buyer PO must belong to the selected Buyer.
Style must belong to the selected order/PO where PO control is enabled.
Consumption must be greater than zero for consumption-based lines.
Additional Qty cannot be negative.
Wastage % must be within the configured maximum.
Packaging ratio and conversion factor must be greater than zero.
Colour and Size must be valid master values.
A material cannot be duplicated for the same BOM + colour + size + applicability unless explicitly allowed.
Approved/Active BOM cannot be directly edited; create a revision.
Posted material transactions cannot be deleted.
Issue cannot exceed available stock unless an authorised over-issue policy exists.
Return cannot exceed outstanding issued quantity.
Actual used + return + wastage must follow configured reconciliation rules.
Closed/cancelled documents cannot be modified.
28. BOM Workflow
DRAFT → SUBMITTED → APPROVED → ACTIVE → SUPERSEDED
Alternative terminal states: CANCELLED / CLOSED.
Only authorised users can approve.
Only Active BOMs can be used for normal material requirement generation.
When a revision is approved, the previous active revision becomes SUPERSEDED.
Approval must store user, timestamp and reason/comment.

33. Multi-Company / Multi-Store
All transactional and master records that require segregation should carry company_id and branch_id. Stock-related records should additionally carry store_id, location_id and optionally rack/bin.
Hierarchy: Company → Branch → Store → Location → Rack/Bin
34. Security & Data Integrity
Use Laravel authorization policies for BOM actions.
Validate company/branch ownership on every foreign key.
Prevent cross-company Buyer/Style/Material selection.
Use database transactions for multi-table posting.
Use soft delete/deactivation for master data where audit retention is required.
Never hard-delete posted transactional documents.
Maintain created_by, updated_by, approved_by and timestamps.
35. Acceptance Criteria
Developer can create a BOM for a Style.
BOM can contain Yarn, Fabric, Trims, Accessories, Packing and General Materials.
Material applicability can be ALL, COLOUR_WISE, SIZE_WISE or COLOUR_SIZE_WISE.
Colour-size matrix calculates material quantities correctly.
Consumption basis works correctly.
Additional and wastage calculations are correct.
Packaging ratio and carton rounding work correctly.
UOM conversions work correctly.
Material requirement is generated from an approved BOM.
Stock and open PO are deducted to calculate net purchase requirement.
BOM revision preserves historical values.
Approval workflow and permissions work.
Audit trail records changes.
Reports can filter by Buyer, PO, Style, Colour, Size and BOM category.
No posted transaction can be silently changed or deleted.
36. End-to-End Reference Flow
Buyer PO → Style → Colour/Size Order Matrix → Active BOM Revision → Yarn/Fabric/Trims/Accessories/Packing/General Material Calculation → Gross Requirement → Stock Check → Open PO Check → Net Purchase Requirement → Purchase PO → GRN → Stock → Material Issue → Production/Packing → Actual Consumption → Return/Wastage → Variance → Costing/Reports
37. Developer Implementation Notes
Use decimal/numeric types for quantities; avoid floating point calculations.
Suggested SQL Server quantity precision: DECIMAL(18,6), percentage DECIMAL(9,4).
Store the calculated values as transaction snapshots for audit and performance.
Use server-side calculation as the final authority; React live calculation is only for UI preview.
Use optimistic locking or version checks to prevent concurrent BOM edits.
Approved BOM revision should be immutable.
All calculation services must be unit tested with colour-size, rounding, UOM and packaging scenarios.
Excel import/export should validate master codes before committing records.
Print/PDF output should show BOM revision, calculation basis, approval details and date.
